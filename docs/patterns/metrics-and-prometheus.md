# Metrics and Prometheus

The reference manager exposes controller-runtime metrics on an optional
metrics port. Metrics are useful for detecting reconciliation failures,
dependency waits, latency, work-queue pressure, and process health, but the
operator must choose its own domain metrics after the external system is
understood.

The example Helm chart keeps metrics enabled so the golden path exercises the
service and NetworkPolicy boundary. The Prometheus integration is opt-in
because `ServiceMonitor` is a Prometheus Operator custom resource and is not
available in an ordinary Kubernetes cluster.

## What the baseline provides

- `cmd/main.go` supports disabling metrics, HTTP metrics, or secure HTTPS
  metrics with Kubernetes authentication and authorization;
- the Helm chart exposes a metrics Service when `metrics.enabled` is true;
- the chart can mount a caller-provided `kubernetes.io/tls` Secret;
- the chart creates the authentication RBAC needed by secure metrics and an
  optional `/metrics` reader ClusterRole;
- the chart can create a `ServiceMonitor` when the target cluster has the
  Prometheus Operator CRDs; and
- the Kustomize bundle includes secure-metrics authentication RBAC and an
  unbound `/metrics` reader ClusterRole.

The generated controller-runtime certificate is convenient for development and
local tests. Production scraping should use a certificate whose trust chain
and DNS names are appropriate for the metrics Service, or configure the
Prometheus integration's trust settings deliberately. Do not copy
`insecureSkipVerify: true` into a production values file without understanding
the consequence.

## Helm configuration

The chart's important values are shaped like this:

```yaml
metrics:
  enabled: true
  secure: true
  port: 8443
  tls:
    certificateSecret: ""
  readerRole:
    create: true
    binding:
      create: false
      serviceAccount:
        name: ""
        namespace: ""
  serviceMonitor:
    enabled: false
    namespace: ""
    interval: 30s
    scrapeTimeout: 10s
    labels: {}
    annotations: {}
    bearerTokenFile: /var/run/secrets/kubernetes.io/serviceaccount/token
    tlsConfig:
      insecureSkipVerify: true
```

`metrics.serviceMonitor.labels` must match the `serviceMonitorSelector` of the
Prometheus resource. Prometheus Operator selects a ServiceMonitor by its
labels, and the ServiceMonitor selects the metrics Service by labels and its
named Service port. A textual port number is not equivalent to the Service
port name.

When secure metrics are enabled, the operator's ServiceAccount needs the
authentication and authorization RBAC generated by the chart. The Prometheus
ServiceAccount needs permission to `get` the `/metrics` non-resource URL. Set
`metrics.readerRole.binding.create` only when the Prometheus ServiceAccount is
known and the chart should create that ClusterRoleBinding; otherwise bind the
generated reader ClusterRole through the platform's monitoring configuration.

The ServiceMonitor's default bearer-token and TLS settings are a development
starting point. For a production installation, use the certificate Secret or
the trust and authentication mechanism required by the Prometheus deployment.
Keep the metrics Service and the Prometheus scraper inside the narrowest
NetworkPolicy boundary that still permits scraping.

## Kustomize configuration

The default Kustomize overlay enables secure metrics on port 8443 and includes
the metrics authentication RBAC. It does not create a ServiceMonitor because
that would make the otherwise portable bundle depend on Prometheus Operator.
Bind `metrics-reader` to the Prometheus ServiceAccount and apply a local patch
for a production certificate when the deployment needs one.

## Verification

Render both chart modes when changing this pattern:

```sh
make helm-lint helm-template
helm template operator-foundry charts/operator-foundry \
  --namespace operator-foundry-system \
  --set metrics.serviceMonitor.enabled=true \
  --set metrics.serviceMonitor.labels.release=kube-prometheus-stack \
  --set metrics.readerRole.binding.create=true \
  --set metrics.readerRole.binding.serviceAccount.name=prometheus-k8s \
  --set metrics.readerRole.binding.serviceAccount.namespace=monitoring
```

The rendered output should contain one metrics Service, one ServiceMonitor,
the secure-metrics authentication RBAC, and the explicitly requested reader
binding. It should not contain a ServiceMonitor when
`metrics.serviceMonitor.enabled=false`.

In a cluster with Prometheus Operator, verify the complete path:

1. the Prometheus resource selects the ServiceMonitor by labels and namespace;
2. the ServiceMonitor selects the metrics Service;
3. its endpoint uses the Service's named `https` or `http` port;
4. the scraper can authenticate and verify the endpoint certificate; and
5. Prometheus reports the target as up and contains the expected
   controller-runtime metrics.

If the target is missing, inspect ServiceMonitor labels, namespace selectors,
Service selectors, named ports, scraper RBAC, TLS trust, and NetworkPolicies
in that order. Use the local Cilium/Hubble workflow to investigate dropped
scrape traffic when a Cilium cluster is available; Cilium is not required for
Prometheus integration.

## Adapting metrics for a new operator

Keep the baseline endpoint and scrape wiring unless the target environment has
a clear reason to differ. Add domain metrics only after deciding what an
operator user needs to observe. Prefer stable, low-cardinality labels such as
controller name, result class, and dependency kind. Do not put resource names,
URLs, external IDs, Secret values, or unbounded error text in metric labels.

Document each domain metric beside the reconciler that owns it, test its
important success and failure paths, and explain how it relates to conditions,
events, logs, and external-system health. A metric should make an operational
question easier to answer; it should not merely mirror every internal branch.
